# 강한 지속 알람 구현 요건

## 결론

사용자가 기기에서 떨어져 있거나 집중하지 않아도 알아차릴 가능성을 높이려면 다음 4계층이 필요하다.

1. **iOS AlarmKit 기반 시스템 알람** — 지원 OS의 주력 수단
2. **네이티브 로컬 알림과 APNs 푸시** — 구형 OS와 동적 일정의 보조 수단
3. **앱 내부 지속 알람 화면·소리·진동** — 앱이 열려 있을 때 확인을 강제하는 수단
4. **서버 확인 상태와 단계적 재알림** — 사용자가 실제로 확인했는지 판단하는 제어 계층

웹/PWA만으로는 무음 모드, 집중 모드, 앱 종료 상태를 넘어서는 신뢰성 높은 알람을 보장할 수 없다. `requireInteraction`도 브라우저 지원이 제한적이므로 보조 기능으로만 사용한다.

## 1. 가장 강한 현실적 구현: AlarmKit

Apple의 AlarmKit은 시스템 수준의 눈에 띄는 알람과 타이머를 제공하며 다음을 지원한다.

- 일회성 및 반복 알람
- 알람 중지와 다시 알림
- 잠금 화면, Dynamic Island, StandBy 표시
- 앱 프로세스가 실행 중이지 않아도 시스템 데몬이 알람 관리
- 필요할 때 집중 모드와 무음 모드를 넘어서는 알림
- 앱별 알람 권한

필요 사항:

- AlarmKit을 지원하는 최신 iOS에서 네이티브 Swift 구현
- `Info.plist`의 `NSAlarmKitUsageDescription`
- `AlarmManager.requestAuthorization()`을 통한 사용자 승인
- 알람 ID를 Supabase와 로컬 저장소에 함께 저장
- 중지·다시 알림용 App Intent
- 카운트다운 UI를 사용한다면 Widget Extension 및 Live Activity 구성
- 미지원 OS에서는 기존 네이티브 로컬 알림으로 자동 전환

나의 비서에서는 “기상·취침·출발·수업·마감처럼 사용자가 강한 알람으로 지정한 일정”에만 AlarmKit을 사용하고, 일반 추천이나 요약에는 사용하지 않는 것이 적절하다.

## 2. Critical Alerts는 별도 선택지

Critical Alerts는 무음 스위치와 방해금지 모드를 무시하고 지정 음량의 소리를 낼 수 있다. 그러나 Apple이 특별 entitlement를 승인해야 한다.

필요 사항:

- Apple에 Critical Alerts entitlement 사용 신청
- 승인된 사용 목적
- `com.apple.developer.usernotifications.critical-alerts` entitlement
- 사용자에게 `.criticalAlert` 권한 별도 요청
- APNs payload 또는 로컬 알림에 critical interruption level과 critical sound 설정

일반 생산성·일정 앱은 생명, 건강, 안전과 직접 관련된 앱보다 승인 가능성이 낮다. 따라서 현재 제품의 기본 계획은 **AlarmKit 우선, Critical Alerts는 장기 검토**가 안전하다.

## 3. 확인 기반 지속 알람 상태 모델

알람이 표시됐다는 사실과 사용자가 확인했다는 사실을 구분해야 한다.

권장 상태:

```text
scheduled → firing → delivered → acknowledged
                    ↘ snoozed → scheduled
                    ↘ missed → escalated
                    ↘ cancelled
```

필수 데이터:

- `alarm_id`
- 사용자·일정·기기 ID
- 예정 시각과 시간대
- 중요도 및 알람 정책
- 전달 채널(AlarmKit, local, APNs, web, in-app)
- `fired_at`, `delivered_at`, `acknowledged_at`
- 다시 알림 시각과 횟수
- 마지막 기기 상태와 권한 상태
- 중복 실행 방지용 idempotency key

사용자가 `확인`, `끄기`, `다시 알림` 중 하나를 누르기 전까지 서버에서는 완료로 보지 않는다. 여러 기기에 로그인한 경우 한 기기에서 확인하면 다른 기기의 후속 푸시는 취소한다.

## 4. 단계적 에스컬레이션 정책

강한 알람은 무한 반복이 아니라 예측 가능한 단계로 강화한다.

예시:

1. 예정 시각: AlarmKit 또는 로컬 알람 1차 발생
2. 1분 미확인: 앱 내부 알람 재개 또는 두 번째 로컬 알림
3. 3분 미확인: APNs 재알림, `timeSensitive` 적용
4. 5분 미확인: 마지막 강한 알림과 앱 배지 증가
5. 이후: 사용자가 설정한 최대 횟수·종료 시각에 따라 중단하고 `놓친 알람`으로 기록

안전장치:

- 기본 재알림 간격은 최소 1분
- 일정별 최대 횟수 설정
- 야간 조용한 시간과 예외 일정 구분
- 운전 중 조작을 유도하지 않는 버튼 구성
- 같은 일정에 대한 로컬·푸시 중복 소리 방지
- 서버 지연으로 이미 지난 알람이 한꺼번에 울리지 않도록 만료 시간 지정
- AI 추천 알림은 강한 알람으로 자동 승격하지 않음

## 5. 장소·이동 알람과의 결합

장소 기반 출발 알람은 예정 시각이 계속 바뀔 수 있으므로 다음 구조가 필요하다.

- 일정 3시간 전부터 위치와 예상 이동시간 재평가
- `남은 시간 - 이동시간 <= 설정 여유시간`이면 출발 알람 확정
- 확정 전에는 서버 푸시 후보만 유지
- 확정되는 순간 AlarmKit/로컬 알람을 가장 가까운 안전 시각으로 등록
- 위치·교통수단이 바뀌면 기존 알람 취소 후 새 ID 또는 revision으로 재등록
- 이미 일정 장소에 있으면 이동 알람 대신 시작 임박 알람으로 변환

백그라운드 위치를 30분마다 정확히 실행하는 것은 OS가 보장하지 않는다. 서버 계산, significant-location-change, 앱 활성화 시 재평가, 예약된 알람을 함께 사용해야 한다.

## 6. 권한·기기 상태 진단 화면

강한 알람 설정 화면에서 다음 상태를 사용자가 직접 확인할 수 있어야 한다.

- AlarmKit 권한
- 알림 권한
- 소리 허용 여부
- Time Sensitive 허용 여부
- 앱 알림이 시스템 설정에서 꺼졌는지 여부
- 백그라운드 새로고침 상태
- 마지막 APNs 토큰 등록 시각
- 마지막 테스트 알람 성공 시각
- 배터리 저전력 모드로 인한 제한 안내

`강한 알람 테스트` 버튼은 1분 뒤 실제 AlarmKit/로컬 알람을 예약하고 사용자가 확인 버튼을 누를 때까지 전체 흐름을 검증해야 한다.

## 7. 현재 프로젝트에 필요한 구현 순서

### 1단계 — 네이티브 AlarmKit 어댑터

- Capacitor 플러그인 `AlarmKitPlugin.swift` 추가
- 권한 요청, 예약, 취소, 조회, 다시 알림 API 제공
- 지원 OS 확인 및 기존 `AlarmPulsePlugin` fallback 연결

### 2단계 — 통합 알람 도메인

- 웹 코드가 특정 플랫폼 API를 직접 호출하지 않도록 `AlarmChannel` 인터페이스 정의
- `alarmkit`, `native-local`, `apns`, `web-push`, `in-app` 구현체 분리
- 동일 알람의 revision과 idempotency 처리

### 3단계 — 서버 확인 상태

- Supabase `alarm_instances`, `alarm_acknowledgements`, `alarm_deliveries` 테이블
- 사용자별 RLS
- 확인·다시 알림·취소 API
- cron/queue 기반 미확인 재알림

### 4단계 — 설정과 진단

- 강한 알람 ON/OFF
- 적용 대상
- 다시 알림 간격·최대 횟수
- 소리 선택
- 권한 상태와 설정 앱 이동
- 1분 뒤 실전 테스트

### 5단계 — 검증

- 앱 실행 중·백그라운드·강제 종료
- 화면 잠금
- 무음 모드·집중 모드
- 네트워크 없음
- 기기 재부팅
- 시간대 변경·서머타임
- 여러 기기 동시 로그인
- 같은 일정 수정·삭제
- 자정 넘김 일정

## 8. 제품 결정

추천 기본 정책:

- 사용자가 직접 `강한 알람`을 선택한 일정만 지속 알람 적용
- AI는 강한 알람을 추천할 수 있지만 자동 활성화하지 않음
- 출발·기상·마감은 별도 프리셋 제공
- 일반 일정은 Time Sensitive 이하
- 5분 내 최대 3회 후 `놓친 알람`으로 전환
- 실제 iPhone에서 테스트가 통과하지 않으면 강한 알람 성공으로 표시하지 않음
